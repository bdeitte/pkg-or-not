# AGENTS.md

Guidance for AI coding agents working in this repository.

## What this is

"Package or Not?" is a static browser game. The player picks a package ecosystem (CRAN, Bioconductor, PyPI, OpenVSX, npm, crates.io, RubyGems, or Mixed bag), guesses Real or Fake for 10 package names, and gets a score and a saying. The results screen can copy a link (`#r=<token>`) that shows the same results to someone else.

Fake names are generated in the browser from a character-level Markov model trained on real names. Names that actually exist are rejected with an exact name list, a Bloom filter, or (npm only) a live registry check.

## Hard constraints

- No backend. The site is static files plus browser-only JavaScript.
- No npm dependencies anywhere, and no build step. Do not add a `node_modules`, bundler, or framework. The one exception is `tools/lint-css.js`, which installs ESLint into a cache folder outside the repo (`~/.cache/pkg-or-not-lint`), never into the repo.
- CRAN, Bioconductor, PyPI and OpenVSX names come from p3m.dev. p3m.dev sends no CORS headers, so the browser can never call it. All p3m data is fetched ahead of time by the prep script.
- Never put the user's email or other personal data in requests. Contact info in the User-Agent comes only from the optional `PKG_OR_NOT_CONTACT` environment variable.
- Values fixed by the spec (keep them unless the spec changes): 10 rounds, 3 to 7 fakes per game, 50 rejected candidates before a round falls back to a real name, 5 percent Bloom false positive rate, 3 second npm live-check timeout in the browser, Bioconductor 3.23 by default, score bands 0-3 / 4-6 / 7-9 / 10.

## Layout

```
prep/                 Node-only prep script (run locally, never in the browser)
  build.js            buildEcosystem() and the CLI: node prep/build.js [eco ...]
  http.js             fetchWithRetry (retries 429/5xx, sets User-Agent), getJson, getText
  markov.js           train(names, { order, minCount })
  preview.js          prints sample fakes and reals from built data
  sources/            one module per ecosystem, plus index.js (SOURCES map) and p3m.js (shared p3m.dev paging helper)
site/                 the deployable static site
  index.html, style.css
  js/ui.js            screens, DOM, keyboard
  js/game.js          rounds, scoring, bands, source picker
  js/generator.js     fake generation and plausibility rules
  js/data.js          loads site/data/<eco>/ and builds the existence check
  js/sayings.js       end-of-game sayings
  js/blocklist.js     offensive-word filter for fakes
  js/share.js         encodes and decodes shareable result links
  js/shared/          modules used by BOTH prep and the browser:
                      ecosystems.js (ids, labels, check type, urlPrefix), normalize.js,
                      bloom.js, markov-sample.js, rng.js (seeded RNG, pick, sample)
  data/<eco>/         generated by prep and committed: model.json and reals.json, plus
                      names.json (cran, bioc), bloom.bin (pypi, openvsx, crates, rubygems)
                      or fakes-verified.json (npm)
test/                 node:test suites
tools/lint-css.js     CSS Baseline check (ESLint installed outside the repo)
```

Ecosystem ids used everywhere: `cran`, `bioc`, `pypi`, `openvsx`, `npm`, `crates`, `rubygems`, plus `mixed` for the Mixed bag option.

## Rules for code

- Everything is an ES module (`"type": "module"` in package.json).
- Code in `site/js/` runs in the browser. Code in `site/js/shared/` must also run in Node, so it may only use standard APIs available in both (no `fs`, `Buffer`, `process`, or DOM).
- `prep/` may use Node built-ins. It imports shared logic from `site/js/shared/` instead of duplicating it, so the prep script and the browser always agree on normalization, Bloom layout and Markov sampling.
- Anything that touches the network takes its fetch or HTTP helpers as injectable parameters with real defaults. Tests pass stubs.
- All registry requests in prep go through `prep/http.js` so they get retries and the User-Agent.
- Name comparisons go through `normalize(eco, name)` in `site/js/shared/normalize.js`.
- Shared result tokens come from untrusted links. `decodeResults` in `share.js` caps the token and inflated sizes and validates every field, including that real-name links start with the ecosystem's `urlPrefix`. Keep those checks when changing the payload, and bump `VERSION` if the format changes. The token is obfuscated, not encrypted.
- Node 24 or newer (see `engines` in package.json).
- If a test fixture is too small for a production default (for example, a tiny Markov model running out of new names), change the test's arguments, not the production default.

## Commands

```
npm test                       # all tests; they never touch the network
node --test test/<file>.js     # one suite
npm run serve                  # static server on http://localhost:8000 (ES modules need http, not file://)
npm run lint:css               # fail on CSS that is not in the widely available Baseline
node prep/build.js cran npm    # rebuild some ecosystems (network)
node prep/preview.js pypi      # sample fakes and reals from built data
```

Prep timing: crates.io is crawled at one request per second (its crawler policy) and takes about an hour. PyPI takes about 10 minutes, npm 10 to 20 minutes. Run long builds in the background.

## Checking UI changes

The node tests do not cover `site/js/ui.js` or the DOM, so check changes to `site/` in a real browser with the chrome-devtools MCP against `npm run serve`:

- Take a snapshot before and after the change, and confirm nothing unexpected changed.
- Run `list_console_messages` and confirm there are no new errors or warnings.
- Check the page at a mobile width (for example 375px) as well as desktop.
- After any edit to `site/style.css`, run `npm run lint:css` and make sure it exits clean. Revert CSS that is not widely available, or guard it with `@supports`.
- For significant changes, run a Lighthouse audit (the MCP `lighthouse_audit` tool) against the local server. All category scores must be 98 or above. Lighthouse output files (`lh*.json`, `*.report.html`) are git-ignored at the repo root.

## Working in this repo

- Write the test first, see it fail, then implement (TDD).
- Commit after every change. Stage files by explicit path; never `git add -A` or `git add .`, because `site/data/` may hold in-progress build output.
- `.superpowers/` is git-ignored scratch space for agent workflows. Do not commit it.
- Do not use bold or italics in docs or commit messages.
